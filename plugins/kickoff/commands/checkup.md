---
description: The repeat visit — a health pass on a project kickoff already onboarded (`.kickoff/notes.md` exists): what to strengthen, honoring past decisions and diffing against the last scorecard. For a project with no ledger yet, use /kickoff:start.
---

Run a strengthening **checkup** on the current project. Do NOT install anything without the user's confirmation.

1. Read `CLAUDE.md` for the stack, the house conventions and the open tasks. If **conventions** aren't documented, sample them (lint/format config, naming, layout) and offer to record them there, so recommendations match the existing style. Everything else about reading a project — dependencies and config files, the installed-tooling inventory, the `.claude/` audit — belongs to `project-setup` Step 1 and is deliberately not restated here.
2. Read the ledger `.kickoff/notes.md` if it exists. **Reconcile, then verify, then skip — in that order.** First collapse the ledger to each item's **latest mention** (a later entry may have installed, declined, cancelled or replaced an earlier line); only then batch-check every path or setting a surviving `installed` entry names and emit a `verified / MISSING` list — checking what the entry was *for*, not just that the path is there (an empty `.git` exists and still leaves you no history to roll back to). Only verified entries may be skipped, and a decayed one outranks any new recommendation (report it, move it back to `open`). A path that only a superseded entry named is **stale, not MISSING**: report it once as a line worth deleting, never re-open it. Then don't re-recommend what's `verified` or **declined**, and surface the items still open after the reconcile. Reading **sibling projects'** ledgers is a separate, consent-gated step — see the `project-setup` roll-up rules before touching another project.
3. **Run the `project-setup` skill against this project**, as written. It owns the inventory, the walk across every dimension, the ecosystem search and the vetting gate; duplicating any of that here is how the two drift apart.
4. Report a concise, prioritized "what to strengthen" — each item tagged (baseline vs discovered) and vetted (skills are lower-risk than plugins/MCP; flag anything account-backed). Render it as a per-dimension **coverage scorecard** (`dimension | status (covered/gap/n-a) | tool | priority`) and persist it in the ledger so the next checkup **diffs against the last** and shows movement. If the last scorecard used other headers or statuses, **map them into this vocabulary and say so in one line**; do not rewrite the old entry. Present this **full plan for one approval** before writing or installing anything — don't act item-by-item. **With no user to approve** (a non-interactive or deliberately read-only run) the pass ends here: write nothing, say the ledger entry was not written, and include the exact text it would have had.
5. Update the ledger: append a dated entry for what was recommended, installed (on confirmation), or declined. Create `.kickoff/notes.md` if it's absent.

**Security stays one line here.** The skill splits it into two dimensions (`security & privacy` and `security (AI/LLM)`); in a checkup they collapse into a single row. Report its status like any other dimension — don't expand it into a full baseline audit mid-sweep, which unbalances the report. If the project is web-facing, flag that it needs a deep pass and point at **`/kickoff:security`** (a focused, fresh-session walk of the security baseline with `file:line` evidence).

Keep it lightweight; skip the ceremony for one-off / throwaway projects.
